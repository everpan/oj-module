## F1 实证探测记录（不修的依据）

假设的修法是 `information_schema` 探测 + 条件 `PREPARE`（MySQL 8.4 无 `ALTER ... ADD KEY IF NOT EXISTS`）。
用 `oj-test-mysql`（mysql:8.4）容器 + vendored `bin/oj`（0.1.129）真机探测：

- `oj migrate` 的迁移 SQL 经**朴素 `;` 切分**后逐条走 `exec_with_params`（`oj-bin/oj/src/migrate.rs:36-42` 注明「语句内不得含分号字面量」）；
- 探测语句 `PREPARE stmt FROM @ddl` 被 mysql_async 的 prepared 协议拒：**1295 (HY000) This command is not supported in the prepared statement protocol yet** → 迁移在 V2 处 abort，模块迁移链整体失败。

即：当前 oj 栈下 MySQL 迁移 SQL **无法**实现该守卫，动态 SQL 是唯一途径而驱动协议封死。
且既有房规明确「mysql 无 CREATE INDEX IF NOT EXISTS → 由迁移账本保证只执行一次」
（`_platform/migrations/0001__baseline.mysql.sql:8` 注释），评审设想的
「下游库已被运维手工建过同名索引」场景在 PR 文档 §7.7 并无依据（§7.7 只声明该迁移属本仓后续动作，未建议手工预建）。
结论：维持裸 `ADD UNIQUE KEY`，文件头补一行声明，风险记入本文档。

**问题分类记录（反常识/与业界不符）**：业界迁移工具（Flyway/Liquibase）通常按语句容错或支持条件 DDL；
oj 的朴素 `;` 切分 + prepared 协议组合使 MySQL 侧条件 DDL 不可表达——这是上游限制，已按 playbook 惯例记录。
