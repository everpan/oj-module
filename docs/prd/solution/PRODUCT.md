> 文档定位：本仓「解决方案生态」的**业务权威说明**，面向产品经理 / 业务方。
> 读者只需理解产品理念、能力边界、关键取舍与演进路线，不涉及技术实现细节与开发操作步骤。

## 1. 产品定位

### 1.1 一句话定位

把 `oj` 宿主 + `ojm` CLI 从「脚手架生成器」升级为一个**自带账户体系、设置中心、审计日志、可扩展登录与解决方案市场的应用框架**，并打通「开发者构建解决方案 → 发布到市场 → 运维安装部署 → 用户使用」的完整链路。第三方业务模块以「`.tgz` + 清单」的形态发布到 CDN，被任意一套框架实例**在线安装、热加载、可回滚**。

### 1.2 解决什么问题

- **重复造轮子**：每个业务模块都要各自实现账号、权限、登录、审计、设置。本产品把这些做成框架级公共能力，解决方案只写业务本身。
- **分发与部署割裂**：过去「怎么把模块发给客户、怎么装到运行中的系统」是一笔糊涂账。本产品提供统一的「市场 → 安装 → 验证 → 回滚」闭环。
- **安全与可信缺失**：任意来源的包直接装入会带来供应链投毒风险。本产品以「签名验签 + 信任库 + fail-closed」守住底线。
- **升级即事故**：版本切换、降级、卸载容易造成数据或权限残留。本产品以「多版本共存 + 锁账本 + 双维度级联」把运维动作变成可逆、可观测的操作。

### 1.3 为谁服务（四类角色）

| 角色 | 关注点 | 在本产品中的旅程 |
|---|---|---|
| **开发者**（solution author） | 把业务打包成可分发方案 | 用 `ojm` 工具链构建、声明清单、发布到 CDN |
| **运维**（operator） | 把方案装到生产、保证可用与可回退 | 通过 CLI 引导部署，或在市场页点按安装/升级/回滚/卸载 |
| **终端用户**（end user） | 用业务功能 | 在菜单/页面直接使用，无感知后端是框架原生还是已装方案 |
| **管理员 / 超级管理员**（admin / superadmin） | 管账号、管权限、管市场与安全设置 | 系统页统一管理；安全敏感动作归 superadmin 独占 |

### 1.4 与 `oj` / `ojm` 的关系

- **`oj`** 是底层运行引擎（外部项目，只读依赖），提供挂载、热更、迁移、签名原语等能力。本产品在其之上构建框架与生态。
- **`ojm`** 是开发者 / 运维工具链（本仓产出），负责构建、发布、安装引导。
- **框架（framework）** 是装在 `oj` 之上的一层：账号、RBAC、设置、日志、LDAP、市场 UI 等**第一方公共能力**，对所有解决方案共享。

## 2. 设计理念

### 2.1 框架化：脚手架升级为框架

`ojm init` 不再只是生成「一套样例代码」，而是生成「一个框架工程」。框架内置账号、RBAC、设置、日志、LDAP、市场等能力——解决方案在这些能力之上生长，而非各自重复建设。

### 2.2 市场即「样例方案」（market-as-sample）

市场本身被设计成一个**普通的解决方案**（独立仓 `oj-market`），它和消费它的第三方解决方案走完全相同的契约。这样做有两个好处：一是市场功能被真实契约完整示范（自证框架能力），二是避免「市场特有权限」被第三方抢注或仿冒。

### 2.3 减法哲学

权限点 / 角色的升级只做「加法 + 元数据覆盖」，声明消失只标 `deprecated` 保留。**唯一允许减法的出口是卸载**。这保证了「升级判决不突变」——已生效的权限不会因作者改了清单而突然失效或复活。

### 2.4 验证双轨

安装不只「把文件放进去」，还要回答「装完真的能用吗」。因此有两道验证：
- **安装期冒烟（smoke）**：装完即跑，自动断言后端可达、前端完整性、注册一致性。
- **按需深检（deep-check）**：管理员主动触发，对路由可达性、RBAC 完整性、设置项完整性、迁移账本、前端完整性做全面体检并出报告。

### 2.5 安全优先：六条硬纪律（不可妥协）

这些是来自历史事故（wiki 原型）的血泪经验，本产品无条件继承：

1. **判权单一出口**：业务代码不自己判权，统一经框架 `assertPermission` 等出口。
2. **禁用闭环三处**：登录、LDAP、SSO 三处签发前都查禁用，漏一处即「禁号可登」。
3. **唯一约束竞态兜底**：建号等写入遇唯一冲突时回查复用，不叠行。
4. **外来号占位 hash**：LDAP/SSO 建号不接管本地号，低信任来源不得冒充本地账号。
5. **审计不反噬业务**：审计失败只告警，挂在成功分支末尾，绝不阻断主流程。
6. **脱敏红线**：审计详情绝不记录口令 / token 本体。

### 2.6 信任与签名：fail-closed

CDN 被视为**不可信通道**。任何包必须经过 sha256 校验与 Ed25519 验签，**任一步失败一律不落盘、不装、不给逃生开关**。未知发布者首次出现时，由管理员人工核对指纹确认（TOFU），绝不「静默信任第一个来源」。

## 4. 关键设计决策与取舍（产品视角解读）

以下从 D1–D17、R1–R31 中精选对业务形态影响最大的决策，用业务语言说明「为什么这么定」。

### 4.1 市场编排归第一方特权，但市场 UI 是普通方案（D5 / R9）

- **决策**：安装编排、任务模型、索引聚合、深检后端等「带平台特权」的能力归框架 `_platform`；展示用市场页本身是一个独立解决方案。编排端点由 superadmin 独占。
- **取舍理由**：特权操作（改文件系统、热更、执行迁移）不能交给普通方案，否则 RBAC 隔离形同虚设。同时 `market` 保持为**保留名**，防止第三方取名 `market` 抢注 `market.*` 权限。
- **业务含义**：普通管理员（admin）能看到市场入口与卡片，但**安装 / 回滚 / 卸载等敏感操作需 superadmin 确认**。后续版本可评估向 admin 开放授权路径。

### 4.2 单一共享根 + 统一前缀（约束 A / §5.8）

- **决策**：所有后端模块统一挂在 `/api`，方案名即模块名即路由段；前端路由统一 `/<name>`。
- **取舍理由**：oj 要求模块名全局唯一，且生成的前端 client 前缀是相对 base 的——一旦给方案另起前缀会导致请求拼错路径、404。统一前缀是唯一自洽形态。
- **业务含义**：方案「一处命名贯穿三处」，开发者心智简单；安装器做保留名与占用检测，避免撞名冒充。

### 4.3 安装顺序：先迁移、后落锁、再热更（D11 / R2 / 约束 B）

- **决策**：安装状态机严格按「迁移成功 → 落锁 → 注册 → 热更」顺序，且入口先做「锁 ↔ 迁移账本」对账自愈。
- **取舍理由**：oj 的热更强制 `migrate verify`-only，带迁移的方案若先改锁后迁移，崩溃窗口会触发全站拒启。顺序颠倒会让整个站点不可用。
- **业务含义**：安装失败有三种语义（锁前清场 / 锁后部分生效 / 切换前复验），运维看到的是「可重试」「已部分生效待修复」「被拦截」而非含糊的「失败」。

### 4.4 禁用 = 摘锁而非删目录（D12 / R5）

- **决策**：禁用方案时，从共享根锁中摘除条目（目录、数据全保留），并同步标记侧车状态与前端。
- **取舍理由**：oj 的锁是原生扁平格式，不能往里塞 `enabled` 标记（会拒启）。禁用必须「非破坏、随时可恢复」。
- **业务含义**：关停某个方案不影响其历史数据与已装目录，重新启用是零成本操作。

### 4.5 多版本共存 + 回滚零成本，但禁止静默降级（B3 / R12）

- **决策**：共享根里多个版本目录天然共存；回滚 = 把锁指回旧版目录。但回滚前必须复验目标版本，若迁移有差异则强告警并要求二次确认。
- **取舍理由**：oj 无「down 迁移」（前向-only），降级可能让旧版运行在新版已改的数据结构上而崩。
- **业务含义**：升级是低成本可逆的，但「跨越迁移差异的降级」会被系统拦下并提示风险，而不是悄悄把系统搞坏。

### 4.6 卸载是唯一的「减法出口」，且双维度级联（D2 / R12 / §5.9.6）

- **决策**：权限 / 角色升级只做加法，只有卸载才做减法；卸载时级联清理「该方案的角色绑定」与「该方案权限点的全部绑定（含自定义角色上的）」。业务表**不删**。
- **取舍理由**：漏掉任一维度，会导致重装方案时旧授权「静默复活」。业务表不可逆，故保留并提示运维手工处理。
- **业务含义**：卸载后重装，绝不会让旧的权限授权自动复活——这是安全红线。

### 4.7 验签 fail-closed，无逃生开关（G4 / R10 / D16）

- **决策**：缺签名、验签不过、格式错一律拒装、不落盘；不提供「允许未签名安装」之类的配置项。
- **取舍理由**：一旦留了开关，事故现场总是「为了方便先打开了」，供应链投毒防火墙形同虚设。
- **业务含义**：市场的可信度由签名保证，管理员不能图省事绕过。

### 4.8 发布方信任：TOFU 双轨 + 吊销只阻断新增（G3 / G5 / D15）

- **决策**：第一方 key 可随宿主预置免确认；未知 key 首次安装由管理员核对指纹后入库（TOFU）。吊销某 key 只阻断新装 / 升级，不影响已装方案继续运行。
- **取舍理由**：纯免 TOFU 会被中间人静默替换发布者；纯严格又要每次搬机器。吊销「只拦新增」兼顾安全与存量可用性。
- **业务含义**：换发布密钥要走「新增 key_id」而非覆盖旧 key；已发布方案的连续性不被一次吊销打断。

### 4.9 验证双轨：冒烟自动、深检主动（B1 / §7）

- **决策**：安装后自动冒烟（四项），管理员可主动触发深检（五项 + 完整性）。
- **取舍理由**：只靠静态签名无法回答「装完真的能用吗」；只靠人工验收则问题发现太晚。
- **业务含义**：装完即给「基本可用」保证；深检是给管理员的一把「全面体检刀」，能产出人话可读、可操作的修复建议。

### 4.10 安装是后台任务、有进度、可取消、可重试（P2-13 / P3-8 / P4-3）

- **决策**：安装设计为异步任务，前端轮询进度；支持取消（清理暂存 + 对账回退）与重入。全异步常驻 worker 架构列为 P5 方向，本期保持「同步 install + 轮询」契约不变。
- **取舍理由**：下载 / 解压 / 迁移是秒级到十秒级，需进度反馈；长任务不应阻塞请求。
- **业务含义**：运维 / 管理员能看到「预检 → 下载 → 校验 → 解压 → 迁移 → 注册 → 前端落位 → 热更 → 冒烟」十阶段进度，失败有可读中文原因与操作指引。

### 4.11 装载策略：默认 `download`，不做 remote-web（Q7 / OJ-5 不提）

- **决策**：默认把方案包下载落盘（共享根即 CDN 的内容寻址缓存）；前端远程 import 模式被砍掉。
- **取舍理由**：remote-web 下 CDN 不可达 = 模块整体不可用，且动态 import 无法带完整性校验；收益有限、风险明显。
- **业务含义**：离线可重放、可用性不依赖 CDN 实时可达。

### 4.12 解压与迁移走系统工具，不做内置黑盒（OJ-1 / OJ-6 终裁）

- **决策**：解压用系统 `tar`（list→validate→extract 三步防 zip-slip），迁移用 `oj migrate` 子进程。
- **取舍理由**：与请求运行时解耦、避免大表迁移占用 JS 运行时与 DB 池、隔离 KillSwitch 误杀与失败隔离。
- **业务含义**：这是工程取舍，对产品形态无直接可见影响——运维只需知道「安装动作是安全、可观测的」。

## 5. 用户角色与权限模型（PM 视角：who-can-do-what）

### 5.1 角色层级

| 层级 | 角色 | 能做什么 |
|---|---|---|
| 平台 | **superadmin** | 一切，外加**安全敏感项独占**：admin / superadmin 成员资格、卸载解决方案、市场安全设置（`market_cdn_url` / 信任公钥等）、全量审计导出 |
| 系统 | **admin** | 日常账号与角色分配、安装 / 禁用解决方案、框架非安全项设置、查全量操作日志 |
| 页面 | **editor / viewer** | 仅作页面级门（体验层，非安全层），供业务方案自行使用 |
| 模块 | **`<name>.admin` 等** | 方案 manifest 声明的模块内权限点，由方案作者定义 |

### 5.2 职权模型要点

- **账号全局唯一所有**：账号与建号权全部归框架，解决方案**零账号表、零建号权**。LDAP / SSO 外来号也由框架登录链统一创建（占位 hash，零初始角色）。
- **登录唯一签发链**：token 签发只发生在框架登录链（本地 / LDAP / 未来 SSO），解决方案拿不到签发能力——这是「登录端点拒装」之外的主防线。
- **判权实时、撤销即强退**：判权以 DB 为权威源 + 进程内短 TTL 缓存，所有写路径同步失效缓存。角色撤销 / 账号禁用下一次请求即生效。
- **JWT 只载身份不载角色**：roles 不进 token claims，避免双写分裂与越权窗口。

### 5.3 判权链（四级自动推导，零配置）

`assertPermission(code)` 命中任一即放行：① 持 superadmin；② 持 admin；③ 持 `<name>.admin`（按 code 首段自动推导模块归属）；④ 精确命中 `sys_role_permission` 绑定。其余一律 403 + 审计。

### 5.4 安全专属出口（superadmin 独占，D11）

四类安全敏感操作**不建模为权限点**——它们物理上不存在于权限表中，因此任何自定义角色都无法通过「绑满权限点」绕过边界。只有 superadmin 能执行，且只有 superadmin 能改 superadmin。

### 5.5 权限数据的两个来源 + 一个不可逾越的边界

- **权限点**只有两个来源：框架内置 `framework.*` + 方案 manifest 声明 `<name>.*`。**运行期禁止注册权限点**（Q10）。
- **角色**有三个来源：框架内置、方案 manifest 声明、管理员在角色管理页新建（只能从「已注册权限点的并集」勾选，可跨模块，机器名强制 `custom.` 前缀）。
- **边界**：方案只能 upsert 自己命名空间的行，物理上碰不到其他方案的数据——「框架管数据、方案管业务」在存储层落地。

### 5.6 升级稳定性与紧急吊销

升级只做加法 + 元数据覆盖，声明消失标 `deprecated` 保留（判权链不过滤、管理 UI 过滤，已绑定继续生效）。紧急吊销时，superadmin 可在角色管理页手动摘除某个 deprecated 权限点的绑定（只减不增），作为单点出事的应急通道，即时生效并留审计。

## 7. 价值主张与对比

### 7.1 核心价值主张

1. **开发者只写业务**：账号 / 权限 / 登录 / 审计 / 设置是框架免费赠品，开发者聚焦业务本身，并以统一清单声明能力。
2. **运维零停机交付**：在线安装、热加载、不重启即生效；升级可回退、降级有护栏。
3. **可信供应链**：签名验签 + 信任库 + fail-closed，从机制上杜绝「装了个被篡改的包」。
4. **安全可观测**：操作日志全量留痕、深检主动体检、权限撤销即强退、安全敏感动作 superadmin 独占。
5. **生态自示例**：市场本身就是一个普通方案，契约被真实示范，第三方作者有可直接对齐的样板。

### 7.2 与「各模块各自实现」的对比（可选）

| 维度 | 各自实现（旧范式） | 解决方案生态（本产品） |
|---|---|---|
| 账号 / 权限 | 每个模块重复造，且各自为政、易漏禁用闭环 | 框架统一，单一判权出口，撤销即强退 |
| 分发部署 | 手工拷贝 / 约定俗成，无版本感 | 市场 + CDN + 清单，版本 / 回滚 / 更新一目了然 |
| 安全 | 信任靠约定，投毒无防线 | 签名验签 + 信任库，fail-closed |
| 升级 | 易出事故、难回退 | 多版本共存、锁账本、强告警护栏 |
| 审计 | 各自打点、难追溯 | 全量操作日志、不可被脚本洪泛淹没 |

## 8. 风险与开放问题

### 8.1 已知限制

- **Windows 支持**：解压依赖系统 `tar`，Windows 需显式 `cmd /c` 模板；列为已知限制（OJ-8 终裁未采纳 Git Bash 探测，保白名单安全边界）。
- **安装仍为同步阻塞语义（契约异步）**：POST 在当前实现下阻塞至安装完成，但契约已是「返 task_id + 客户端轮询」；全异步常驻 worker 留 P5（见 P4-3）。
- **索引 / 信任库形态调整**：索引签名已在 P3 落地，但「更强治理（官方/第三方分级、来源白名单）」属于 P5+ 市场治理范畴。
- **业务表不删**：卸载保留业务数据，需运维手工清理——这是不可逆风险的有意取舍（Q4）。
