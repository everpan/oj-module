# oj 0.1.50 对齐评审与更新计划（packages/cli）

日期：2026-10-06
评审对象：`packages/cli`（`@oj-module/cli`，bin = `ojm`）
对齐基准：oj **v0.1.50**（二进制 `~/.local/bin/oj`，发布文档 `~/.local/share/oj/devkit/`）

## 0. 实施记录（2026-10-06，分支 `feat/oj-0.1.50-alignment`）

用户裁决：**不考虑兼容性，以 oj 最新版本为准**。本日落地 M1 全部 + M3 部分，并实测出三个
计划里没预料到的问题。

### 0.1 版本门禁的定值被实测推翻（原定 0.1.50 → 改为 0.1.32）

原计划按「本机 oj 是 0.1.50」把 `MIN_OJ_VERSION` 定为 0.1.50。逐个下 `@oj-bin/oj@<v>`
跑 `oj --help` 后修正：

| 版本 | 启动子命令 |
|---|---|
| 0.1.13 / 0.1.16 / 0.1.19 / 0.1.24 / 0.1.26 / 0.1.28 | `server` |
| 0.1.32 / 0.1.50 | `serve` |

改名落在 **(0.1.28, 0.1.32]**，故下限取 **0.1.32**。取 0.1.50 会让 `ojm vendor` / `ojm init`
彻底失去可用来源——npm 通道 `@oj-bin/oj` 的 `dist-tags.latest` 就是 **0.1.32**（已发布版本
仅到 0.1.32，本机 0.1.50 来自其它渠道）。**ojm 的开发基准仍是 0.1.50，0.1.32 只是兼容下限。**

### 0.2 实测发现：oj 的 swc minify 会压坏产物（原计划未列，P0 级）

`ojm build` 走 `oj build`，而 oj 默认开 minify。实测两处坏法（0.1.32 与 0.1.50 均复现）：

1. `const rows = await db.query(...); const row = rows[0];`
   → 压成 `await db.query(...)[0]`。下标先于 `await` 求值，在 Promise 上取 `[0]` 得
   `undefined` → 登录端点恒 401 `invalid credentials`。
2. `if (Array.isArray(p)) roles = p;`
   → 压成 `Array.isArray(p) && roles = p`。赋值作 `&&` 右项缺括号 →
   `SyntaxError: Invalid left-hand side in assignment`，端点 500。

处置：`ojm build` 一律加 `--no-minify`（正确性优先于体积，代码里已注明两种坏法与复现版本，
上游修好即可撤旗标）。这直接修好了 `tests/integration/uni-dev-smoke.test.ts` 的 preview 用例。

### 0.3 实测发现：oj 与 plugins 必须整套同版本

把本机 0.1.50 的 `oj` 盖到 npm 装的 0.1.32 工程上会报
`plugin ABI mismatch: plugin=9 host=11`。`bin/{oj,plugins}` 必须同版本整体替换（playground
已按此处理）。

### 0.4 实测发现：playground 的迁移文件重复触发 S007

`api/src/web/migrations/` 下有两个序号 0002 做同一件事的文件（`add_avatar_base64` 与
`add_users_avatar_base64`），oj 的 S007 会拒（同名 desc 才允许方言覆盖）。已删重复项。
另修正 `oj build` 漏传 `-c` 导致 config 读不到（tasks 镜像目录回落默认、sql_guard 校验失效）。

## 1. 结论摘要

`packages/cli` 当前实际是**按 oj v0.1.11 开发的**，与最新 0.1.50 之间有 39 个小版本的漂移。
其中最要命的一条是**已实测的破坏性故障**：oj 的子命令已从 `server` 改名为 `serve`，
而 `ojm dev` / `ojm preview` 仍在 spawn `oj server` —— 配合 `ojm vendor` 默认追 `latest`
的版本策略，任何新装/重装工程拿到的就是 0.1.50，全栈形态**直接不可用**。

除止血项外，oj 在 0.1.12→0.1.50 期间补齐了大量能力（入参契约 `.schema`、`oj openapi`、
cookie 会话 + CSRF、blob 直传与三件套、流式响应/SSE、multipart 流式落盘、凭据密封、
多静态站点与 meta 注入、CORS），这些能力 `packages/cli` 要么未纳、要么自建了重复实现。
契约子系统（`src/contract/`）目前只覆盖 oj 的「路由 + 入参 + 出参信封」切片，是最大的
一处能力洼地，也是本次更新的最高价值点。

建议按 **M1 止血 → M2 契约打通 → M3 模板与配置面 → M4 命令面补齐 → M5 门禁与文档**
五个里程碑推进，M1 单独一个 PR 先发。

## 6. 未决问题

1. **子命令改名的时间点未定位**：devkit 四件文档里没有 `server`→`serve` 的变更记录（README 自称逐条对齐，但 0.1.36/45/48/49 无任何痕迹）。需向 oj 侧确认改名版本，才能决定 ojm 是否需要「按版本选子命令」的兼容分支（老工程可能仍钉 0.1.1x）。
2. **ojm 自建 html-transform 是否退役**：取决于下游是否依赖 `web.config.ts` 钩子的运行时能力（oj 的 `html_meta_handler` 只做 meta，不做任意 HTML 变换）。需确认下游用法后再定。
3. **契约 `.schema` 与后端手改 handler 的冲突**：stub 是 sha256 指纹幂等（人编辑过永不覆盖），`.schema` 的更新策略需要单独设计（建议独立文件 `api.schema.ts` 由 handler 引用）。

## 7. 分类备注（反常规/与业界不符）

- oj 的 `oj serve` 子命令在文档中被全程写作 `oj serve`，但 packages/cli 与测试里写的是 `server`，说明**改名未被下游感知**——上游无 changelog、下游无版本门禁，两侧同时失守。
- `server.base` 与 `server.api_prefix` 是同一键的旧/新名，并存会报 duplicate field；而 `oj serve --help` 的 `-b` 说明里仍写 `server.base`，文档自身不一致。
- `js_heap_limit_bytes`（0.1.40）在 api-manual §10 的 server 表里**漏列**，只有 §13 限制表有——文档不能作为配置面唯一真源。
