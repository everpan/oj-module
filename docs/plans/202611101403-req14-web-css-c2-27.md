## 1. 问题（REQ 复述 + 本仓代码核实）

`solution.yaml` 的 `web.css` 让作者手填产物路径（`modules/<name>/<version>/xxx.css`），
但 vite 产物 css 的文件名由构建器决定，作者无从预知；`ojm build --bundle` 的 C2-27
成品存在性复核（`bundle.ts:345`）拿手填路径对磁盘，必然失败（oj-dbx 0.1.0 实测复现）。
同时 css 存在**两套真相源**且互相脱节：

| 场景 | css 来源 | 后果 |
|---|---|---|
| 站点 `ojm build`（module-build.ts:344） | vite 产物自动扫描，写进 modules.json | ✅ 正确真源 |
| 方案包安装（deploy-web.ts:179） | manifest `web.css` **手填透传** | 手填错 = modules.json 指向 404 css（静默缺样式）；不声明但 entry import 了 css = 安装后**丢 css 链接**（更隐蔽的反向缺陷，REQ 未发现） |
| `--bundle` C2-27（bundle.ts:345） | manifest 手填路径对磁盘 | 手填即炸（本单） |
| 重建合并（installed-merge.ts:86） | 已装版本目录顶层 `*.css` 扫描 | ✅ 正确真源 |

结论：`web.css` 手填字段是唯一错误源，其余三处早已自动化。**修复 = 把第四处（安装）
也对齐到扫描口径，废弃手填字段**——REQ 方案 A 的安装侧实质 + 方案 B 的校验源对齐。

## 2. 定案（BDD）

### D1 deployWeb css 自动扫描（deploy-web.ts）

- 当 包内 `web/modules/<name>/<version>/` 顶层存在 `*.css` 且 manifest **未声明** `web.css`，
  则 modules.json 条目与旁车登记 `css: ["/modules/<name>/<version>/<file>.css", …]`
  （readdir 字母序稳定；与 site build / installed-merge 同口径）→ **修复「不声明即丢链接」**
- 当 manifest 声明了 `web.css` 且树内有对应文件，则登记值与声明一致（存量行为不变的兼容形态）
- 当 manifest 声明了幽灵 css（树内无此文件），则忽略不登记、安装成功（不再透传 404 路径）
- 当 树内无 css 且未声明，则 `css` 字段缺省（既有形态不变）

### D2 bundle C2-27 校验源对齐（bundle.ts）

- 当 `web.entry` 声明路径在包内 web 树不存在，则**仍失败**（entry 名固定 `entry.js`，
  手填确定性强，契约保留）
- 当 `web.css` 声明（无论是否存在对应文件），则**不再失败**，改为废弃告警（值忽略，
  指引删除字段）；oj-dbx 现场复现即消解

### D3 文档与契约

- `manifest-contract.ts` C2-27 css 形状规则**保留**（存量包零破坏；仅 bundle 处软化为告警）
- `docs/prd/solution/ARCHITECTURE.md` web.css 行改「已废弃（0.2.82）：产物 css 自动登记，
  勿手填」
- REQ §3 附带建议（C2-12a/12c 前移普通 build）**已在 0.2.81 落地**（`assertSolutionFileContract`，
  cli.ts:149），无需再动——回应 REQ 时说明

### 反目标

- 不做 css 重命名归一（`<name>.css` 强改）：vite 资产名即真源，重命名引入第二个真源
- 不在 preflight 补 css 校验：扫描值必然在盘，无需校验
- 不动 smoke.ts：它读 modules.json 条目 css 验落位——扫描值必然通过
