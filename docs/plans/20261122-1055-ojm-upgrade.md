# `ojm upgrade` 子命令计划（2026-11-22 10:55）

## 背景

用户侧工程以 `ojm init` 脚手架生成，`@oj-module/cli` + `@oj-module/runtime` 以**精确版本**钉在
工程 `package.json` devDependencies（lockstep 发版）。CLI 升级目前全靠人工：改两个版本号、
`pnpm install`、再跑一次 `ojm init --yes` 恢复保护根（src/app、src/oj-market）——步骤多、
无备份、失败无回退。需要一条以已发布最新版本为准的自动升级路径（用户侧通常没有源码）。

## 目标（SMART）

`ojm upgrade [--yes] [--to <version>] [--registry <url>]`：

1. **先评估后执行**：评估阶段纯只读——当前版本 → 目标版本、保护根相对**新版本模板**的漂移
   预览、config.yaml 顶层键差集提示、明确的「不受影响面」声明（自定义模块 / config.yaml /
   enabled 方案与 DB / cdn / dist）。
2. **以已发布最新版本为准**：registry packument（`dist-tags.latest`）裁决目标版本；
   `--to` 可钉其它已发布版本；目标版本不存在 → 拒绝（exit 1，给原因）。
3. **不影响现有配置与 enabled 模块**：改动面只有 `package.json` 两个 devDep + `node_modules`
   （pnpm）+ 保护根（新 CLI 的 `init --yes` 语义）+ 备份目录 `.ojm-upgrade/`；`config.yaml`、
   自定义 `src/<name>`、overlay DB 行一律不碰（`ojm init` 本就如此，升级沿用并显式声明）。
4. **备份 + 失败回退 + 原因**：执行前备份（sha256 清单），任一阶段失败回滚到备份并报告
   失败阶段、原始错误、备份路径；备份保留最近 3 份（自动轮换）。

## 非目标

- 不回滚 `bin/`（oj 二进制）：能力闸门（MIN_OJ_VERSION）保证新版 oj 只前进到兼容版本，
  且 bin/ 体积大；升级失败时新版 oj 与旧框架可共存（声明在输出里）。
- 不做 DB 迁移：overlay/生命周期表由站点运行时自行迁移（既有机制）。
- 非交互确认只走 `--yes`：无 `--yes` 时打印评估后退出并提示加 `--yes`（不引 readline）。

## 命令面

```
ojm upgrade [--yes] [--to <version>] [--registry <url>]
  评估（只读）→ 备份 → pnpm add 新 cli/runtime → 新 cli 跑 init --yes → 后置漂移检
  失败任一阶段：回滚备份 + 报告（阶段 / 原始错误 / 备份路径）
```

目标版本裁决：`--to` > registry `dist-tags.latest`。runtime 与 cli 同版本（lockstep），
`pnpm add -D @oj-module/cli@<to> @oj-module/runtime@<to>`；runtime 该版本不存在时
回退其 `dist-tags.latest`（评估阶段在 packument 里预判并在输出中注明）。

执行序（每步可失败、可回滚）：

| 阶段 | 动作 | 失败回滚 |
|---|---|---|
| S1 评估 | fetch 两个 packument + 下载目标 cli tgz 到临时目录解包（templates 漂移对比用） | 零写入，无需回滚 |
| S2 备份 | 备份清单文件（package.json、pnpm-lock.yaml、pnpm-workspace.yaml、config.yaml、web.config.ts、tsconfig.json、src/tsconfig.json、src/.ojm-builtin.json、src/app/、src/oj-market/）→ `.ojm-upgrade/backup-<ts>/` + manifest.sha256.json；轮换保留 3 份 | 备份自身失败 → 中止（零改动） |
| S3 换版 | `pnpm add -D @oj-module/cli@<to> @oj-module/runtime@<rt>` | 恢复 package.json + lock + `pnpm install` |
| S4 重脚手架 | spawn `node <proj>/node_modules/@oj-module/cli/bin/ojm.mjs init --yes`（新 CLI 自恢复保护根） | 同上 + 还原保护根目录 |
| S5 后置检 | 漂移检（相对新模板）必须为零，否则回滚 | 同 S4 |

## BDD 用例（TDD 锚）

```gherkin
功能: ojm upgrade 框架升级
  背景: 工程 package.json devDependencies 钉 @oj-module/cli = 0.2.97，
        registry 最新 = 0.2.98；保护根 src/app 有 1 个本地修改文件

  场景: 只评估不执行（无 --yes）
    当 运行 ojm upgrade（无 --yes）
    那么 输出含 当前版本 0.2.97 → 目标 0.2.98、漂移预览（modified=1）、不受影响面声明
    且 package.json / src/app / .ojm-upgrade 均未被写入
    且 退出码 0 并提示「如需执行请加 --yes」

  场景: 已是最新版本
    当 运行 ojm upgrade（当前 = latest）
    那么 输出「已是最新」且零写入，退出码 0

  场景: --to 指定不存在的版本
    当 运行 ojm upgrade --to 9.9.9
    那么 拒绝并列出可用的最近版本，退出码 1，零写入

  场景: 完整升级成功路径
    当 运行 ojm upgrade --yes
    那么 依次：评估输出 → 备份落盘（manifest.sha256.json 可校验）→
      pnpm add 收到 cli@0.2.98 + runtime@0.2.98 → init --yes 由 0.2.98 包执行 →
      后置漂移检为零 → 输出「升级完成」
    且 自定义模块 src/my-mod、config.yaml、cdn/ 内容逐字节不变

  场景: pnpm add 失败回滚
    当 pnpm add 以非零退出
    那么 package.json 与 pnpm-lock.yaml 恢复备份内容（sha256 校验），
      回滚后跑一次 pnpm install，输出含 失败阶段=S3、原始错误、备份路径，退出码 1

  场景: init --yes 失败回滚
    当 新 CLI 的 init --yes 抛错
    那么 保护根目录恢复备份内容，package.json/lock 恢复并 pnpm install，
      输出含 失败阶段=S4 与原因，退出码 1

  场景: 后置漂移检失败回滚
    当 init 完成后相对新模板仍有漂移
    那么 全量回滚（同 S4）并注明「新基线仍有漂移：<文件>」，退出码 1

  场景: enabled 方案不受影响
    当 工程已装方案（DB overlay 行 enabled=1）且升级成功
    那么 DB 行数与 enabled 位全程不变（升级命令零 DB 接触）

  场景: 备份轮换
    当 .ojm-upgrade 已有 3 份备份再升级
    那么 最旧一份被清理，备份总数 ≤ 3
```

## 风险与备注

- 新 CLI 的 `bin/ojm.mjs` 经 `import.meta.resolve("tsx")` 自取 tsx（cli 自身 dependency），
  pnpm 严格布局下从新包位置可解析——S4 spawn 该 bin，不引旧进程代码（避免版本串味）。
- 评估阶段下载 tgz 只为模板漂移对比；S3 的 pnpm add 会再拉一次（pnpm store 去重，可接受）。
- registry 默认 `https://registry.npmjs.org`，与 `ojm install --registry` 同语义。
